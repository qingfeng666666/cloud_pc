# 云电脑总体设计

更新日期：2026-10-07

本轮范围：独立Android与Windows管理界面只访问同设备服务。从机设备通过本机从机沿既有主从连接取得信息；主机设备通过本机主机取得信息。远程API与令牌已撤销。不移植ALXR、不增强长期断线重连。构建验证见[本轮记录](../docs/dev/management_ui/VERIFICATION_20261007.md)。

## 1. 总体结构

云电脑分为三个部分：**主机程序、从机程序、管理界面**。三者按职责划分，不按设备划分；管理界面不必与主机程序运行在同一台设备。

本文采用“总述 → 分项设计”的总分结构，是后续实现的架构依据。本文描述目标设计，不表示现有各平台版本已全部实现。

| 部分 | 主要职责 | 详细设计 |
| --- | --- | --- |
| 主机程序 | 主动发起并维持连接、转接消息、汇总信息、提供管理 API | [主机程序](design/HOST_PROGRAM.md) |
| 从机程序 | 接受主机连接、执行授权指令、返回结果和采集数据 | [从机程序](design/SLAVE_PROGRAM.md) |
| 管理界面 | 展示设备和汇总信息、提交操作、设置活动状态 | [管理界面](design/MANAGEMENT_UI.md) |

```text
管理界面（本机或其他设备）
           ⇅ 主机管理 API
       主机程序
       ├── 主动建立并维持连接 ⇄ 从机 1
       ├── 主动建立并维持连接 ⇄ 从机 2
       └── 主动建立并维持连接 ⇄ 从机 N
```

连接由主机发起，但连接上的消息是双向的。从机可以在已建立的连接上发送结果、事件、采集数据和转接请求，这不等于从机主动建立连接。

### 1.1 主机程序：连接、转接和信息汇总中心

主机程序可以独立运行，不依赖管理界面。主要功能：

- 主动连接指定 IP 的从机，维持连接、检测断线并重连。
- 将管理界面的操作发送给从机，接收执行结果。
- 转接从机之间的消息：从机 1 提供从机 2 的已知 IP，主机校验后转发，并返回结果。
- 管理从机活动状态，主动启动、停止截图和音频同步。
- 汇总从机状态、截图、音频、任务输出和日志，供管理界面或主机内部程序使用。
- 校验连接身份、操作权限和转接目标。

### 1.2 从机程序：本地指令执行与数据采集端

从机程序运行在被操作的设备上，负责执行主机指令并返回信息。主要功能：

- 监听服务端口，只接受授权主机的通信。
- 执行文件操作、任务及本地应用转发等指令。
- 根据主机要求采集屏幕、音频等数据。
- 返回执行结果、采集数据、事件和错误。
- 需要向其他从机发送消息时，将已知目标 IP 和消息提交给主机，不直接连接其他从机。
- 遵守所在设备的系统权限，报告不支持的能力或权限不足。

### 1.3 管理界面：用户操作与信息展示端

管理界面可以与主机同机，也可以运行在其他设备上，通过主机访问从机。主要功能：

第一版首页参考 ALXR 默认控制界面，只保留“从机界面1”“从机界面2”“主机 Codex 界面”三个入口。两个从机页面展示主机汇总的每秒截图；Codex 页面参考安卓“打开当前窗口”，提供每秒更新的文字、顶部输入框、SEND、STOP 和历史滚动。详细交互及验收见[管理界面分项设计](design/MANAGEMENT_UI.md)。以下通用功能不要求全部出现在第一版首页。

- 配置从机地址，查看连接状态和设备能力。
- 设置从机活动状态及采集参数。
- 展示主机汇总的截图、音频状态、任务输出和日志。
- 提交文件、任务及其他操作，查看执行结果。
- 不负责维护从机连接，也不绕过主机直接操作从机。

上述功能按目标模块归属划分；现有程序尚需按这些边界完成解耦和统一，不能将功能归属说明视为已实现清单。

## 2. 必须遵守的边界

1. 主机是连接的主动发起方，负责连接、维护、重连和断线状态汇总。
2. 从机只接受授权主机的通信，不接受其他从机直接通信。
3. 管理界面只通过主机操作从机，不绕过主机直连从机。
4. 从机间消息统一经主机转接；请求方必须事先知道目标从机 IP。
5. 主机不依赖从机扫描、发现或报告其下级设备 IP。地址由主机配置、管理界面输入或请求方已知信息提供。
6. “设为活动”由主机驱动截图、音频等信息采集；管理界面和主机本身均可使用汇总结果。
7. 平台权限仍然有效；连接成功不等于拥有全部文件、摄像头、麦克风或任务执行权限。

“只接受主机”需要身份认证和授权校验，不能仅凭消息中的 source 字段或声称的 IP 判断。具体认证机制需在实现阶段落地。

## 3. IP 转接

这里的 IP 转接指应用层消息路由，不是自动建立 VPN、网络扫描或开放任意端口代理。

例如从机 1 要向从机 2 发送消息：

```text
从机 1（已知从机 2 IP）
  → 在主机已建立的连接上提交目标 IP 和消息
  → 主机验证来源、目标及操作权限
  → 主机使用自己与从机 2 的连接转发
  → 从机 2 返回结果给主机
  → 主机将结果返回从机 1
```

从机 2 接收的网络通信仍来自主机。主机可附带经验证的原始请求方标识，但这不会授权从机 1 直接访问从机 2。

目标未知、不允许访问或无法连接时，返回明确错误；不擅自扫描其他地址。通过从机访问其网络下的设备属于另一个受控代理能力：同样要求已知目标 IP 和显式授权，不由从机自动上报地址。

## 4. 信息汇总与活动状态

主机为每个从机维护连接状态、能力、活动状态、截图、音频、任务结果和诊断信息。

管理界面设置从机为活动后，由主机发起采集配置或采集请求，按配置同步截图和音频。可以有多个活动从机，不默认限制为一个。

- 截图：汇总最新图像、采集时间、序号和错误状态；频率可配置。
- 音频：由主机启动与停止采集，汇总音频分片及格式、时间、序号等信息。
- 消费者：管理界面、主机内部处理程序，或者经授权访问主机 API 的其他程序。
- 取消活动：主机停止对应采集。断线后标记数据过期，不将旧数据显示为实时数据。
- 管理界面关闭不等于自动取消活动；活动状态由主机维护，停止条件应显式配置。

截图、音频可以使用持续推送或主机请求响应；无论采用哪一种，采集均由主机授权启动。额外媒体通道也必须由主机建立或协商，不允许成为从机之间的旁路。

## 5. 通信基础与部署

现有 CLDC 消息头为 12 字节：Magic（4 字节，CLDC）、版本（2 字节）、类型（2 字节）、正文长度（4 字节），使用网络字节序。常规正文为 UTF-8 JSON；具体文件、媒体载荷以对应消息定义为准。

现有从机通常监听 TCP 9527，主机主动连接。常驻主机 HTTP API 常用 127.0.0.1:8765。这些是现状入口，不是不可修改的协议约束。

远程管理界面不能直接访问其他设备的 127.0.0.1。主机需要提供受保护、可达的管理 API，或通过受控隧道访问；不得直接将无认证的本地 API 暴露到公网。

已有文件、任务、AR 和采集消息应继续按真实实现整理。桌面主机与 Python 从机已新增 0x0701/0x0781 编号 RPC、0x0702/0x0782 IP 转接，首批只支持 file.list、file.stat，默认拒绝转接，需显式授权；详见[实现与验证说明](../desktop_version/README.md)。其他平台与常驻 8765 服务尚未接入，不代表统一转接已经全平台完成。

## 6. 现有实现与迁移边界

已有 Windows、HoloLens/UWP、Android 从机能力不同，不能将一个平台的能力视为所有平台均已支持。

后续需要逐项核对并实现：

- 主机服务与管理界面的职责及部署解耦。
- 从机对主机身份的认证、访问控制及拒绝其他从机直连。
- 统一转接请求、返回关联、目标授权与错误处理。
- 主机统一维护活动状态及截图、音频的采集和汇总。
- 将实验中直接连接其他从机的路径迁移到主机转接路径。
- 按新架构更新使用说明和实际协议定义中的旧角色描述。

旧的 ALXR 或其他程序直连远端从机的实验路径不能视为符合本设计；需后续迁移。同设备的本地应用接口另行定义权限，不自动获得从机间直连权限。

设计文档与实现进度分别维护；设计要求不能直接视为已实现功能。当前源码进度见上述说明，未改变正在运行的服务或设备安装包。

## 7. 验收原则

1. 管理界面位于另一台设备时，仍可通过主机查看并操作从机。
2. 所有主机—从机连接由主机发起；断线由主机处理并报告。
3. 从机 1 的直接连接被从机 2 拒绝，经主机的授权转接成功。
4. 请求方提供已知目标 IP；未知、离线、越权目标分别返回可诊断错误。
5. 设置活动后，由主机启动截图、音频同步；取消后停止。
6. 汇总数据包含时间及来源，断线和陈旧数据不会伪装成实时结果。
